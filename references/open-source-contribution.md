# 上游开源贡献工作流

## 适用范围

用户要求为第三方或公开上游仓库调查 Issue、实现修复、执行严格审查并创建 Pull Request 时，使用本流程。

目标不是“尽快产出一个 PR”，而是证明以下事实：问题仍存在、改动没有重复别人工作、修复覆盖真实契约、验证证据与结论一致、维护者可以低成本审查和回滚。

## 1. 判断 Issue 是否仍值得做

### 读完整上下文

- 阅读 Issue 正文、全部评论、时间线、标签、负责人和关联开发记录。
- 记录明确的复现步骤、期望行为、受影响版本和维护者给出的范围限制。
- 不把 `open`、`help wanted` 或长期无人回复直接解释为“当前没人处理”。

### 搜索所有公开实现

至少从四条线索搜索 Open、Draft、Closed 和 Merged PR：

- Issue 编号，例如 `#1234`。
- Issue 标题中的稳定短语。
- 受影响的类型、函数、配置键或错误文本。
- `fix`、`resolve`、`localize`、`regression` 等与问题语义相关的词。

搜索结果必须阅读正文、评论和 diff，不能只看标题。标题不同的 PR 也可能已经覆盖同一根因；关闭的 PR 可能解释了维护者拒绝的方案。

### 核对最新主线

- 以最新上游默认分支为准，检查相关实现、调用链和测试。
- 如果 Issue 描述的代码已经不存在，继续追踪替代实现，而不是在旧路径上制造兼容层。
- 能运行复现时先复现；不能运行时，用当前源码、历史测试和维护者说明建立证据边界。

完成调查后，将 Issue 归类：

| 分类 | 动作 |
| --- | --- |
| 当前仍可复现且没有重叠 PR | 进入实现 |
| 当前主线已经修复 | 不制造冗余 diff；报告证据并建议关闭 Issue |
| 已有活跃或等价 PR | 不抢占；评审、补测试或选择其他 Issue |
| 方案存在维护者争议 | 先在 Issue 确认方向，再写代码 |
| 无法复现且证据不足 | 继续调查或明确阻塞，不把猜测提交成修复 |

对外只能说“未发现公开关联 PR、认领评论或主线修复”。除非有直接证据，不声称“绝对没人正在处理”。

## 2. 控制 PR 范围

默认一个 Issue 一个 PR，使审查、回滚、变基和择取彼此独立。

只有同时满足以下条件时才合并多个 Issue：

- 它们依赖同一个不可分割的状态机、共享契约或原子改动。
- 拆分会产生不能独立编译、不能独立验证或必然重复的中间状态。
- PR 正文能解释耦合原因，并为每个 Issue 提供独立验证证据。
- 用户明确要求合并，或仓库维护者已有同类合并惯例。

“顺手一起做”“都在同一个产品里”或“能少开几个 PR”不构成合并理由。不要混入格式化、重命名、依赖升级和无关清理。

## 3. 建立干净工作区

- 从已确认的上游仓库创建 Fork，并保留原仓库为 `upstream`、个人仓库为 `origin`。
- 从最新上游默认分支建立任务分支，不从陈旧本地主线继续开发。
- 修改前记录子模块、生成物和工作树状态；用户已有改动一律保留。
- 使用仓库已有工具链和脚本。临时下载的编译器、缓存和制品放在隔离目录，不污染全局环境。
- 下载外部工具时使用官方来源与校验值；任务结束后清除一次性制品，但不删除仓库需要的缓存或用户数据。

## 4. 修复真实契约

### 先建立失败证据

Bug 修复必须先得到以下至少一种证据：

- 可重复触发的运行场景。
- 能在修复前失败的行为测试。
- 当前代码路径与状态不变量之间的明确冲突。

用户已经报告的运行事实视为真实，不为了形式重新质疑；测试用于保护修复契约，而不是否定用户观察。

### 修根因而不是屏蔽症状

- 修改拥有错误状态或行为的源头，不在展示层隐藏错误。
- 不通过吞异常、放宽断言、特殊输入或永久兼容壳制造绿色结果。
- 状态机修复要覆盖进入、恢复、取消、重试和清理；数据路径修复要覆盖原子性、容量边界和失败后的可恢复性；配置迁移要覆盖用户数据保留、幂等和旧版本残留。
- 当前主线已经实现的部分保持不动，不为了让分支“有改动”而重复编码。

## 5. 严格审查门禁

普通低风险改动按风险执行一次有效审查即可。用户明确要求反复审查，或改动跨越并发、持久化、网络、权限、配置迁移等高影响边界时，执行三轮相互独立的审查。

### 第一轮：Issue 契约

- 按 Issue 或独立子系统分配评审范围，可以并行。
- 检查修复是否覆盖正文与评论中的全部验收条件。
- 检查测试是否能在旧实现上失败，是否只断言可观察行为。

### 第二轮：交叉风险

- 让未参与首轮实现判断的人或隔离上下文检查整体 diff。
- 重点检查竞态、生命周期、容量、数据保留、安全边界、回滚和测试隔离。
- 核对各子修复组合后是否产生新的共享状态或顺序依赖。

### 第三轮：最终集成

- 只基于最终 diff 和最终测试结果审查，不复用已过期快照。
- 检查编译级问题、遗漏调用点、临时制品、无关文件和 PR 范围。
- 结论必须是明确批准，或列出仍需修复的发现。

评审发现修复后要重新通过发现该问题的门禁。三个 Agent 同时启动、同一条意见被重复三次、Bot 正在处理或因额度失败，都不算三轮审查完成。

## 6. 形成可信验证证据

验证按风险逐层扩展：

1. 运行改动契约对应的最小测试或真实复现场景。
2. 运行受影响模块的现有测试。
3. 涉及公共接口、编译边界或打包时执行构建。
4. UI、CLI 或服务行为必须在真实表面做最小 Smoke；仅编译通过不能替代行为验证。

验证报告必须区分：

- 本次新增或修改的测试是否通过。
- 受影响模块是否通过。
- 全仓测试是否执行。
- 哪些失败是当前主线既有问题，以及判断依据。
- 是否排除了文件、目标或可选构建步骤，为什么排除。

排除既有坏测试后构建成功，只能写“在明确排除项下构建成功”，不能写“全量测试通过”。一次编译器崩溃、网络失败或工具缺失不等于代码失败；先定位故障层，再选择等价且诚实的验证方式。

## 7. 提交和 Pull Request

提交前：

- 检查最终 diff，只暂存目标文件。
- 清除临时工具、日志、制品和包含凭据的文件。
- 确认没有覆盖用户工作，没有意外更新子模块或锁文件。
- 按用户授权边界执行 Commit 和 Push；没有授权时停在已验证 diff。

PR 必须沿用仓库模板，并包含：

- 每个改动的行为结果和原因。
- `Closes #...` 或仓库约定的关联方式。
- 实际执行的测试或 Smoke，以及真实结果。
- 未执行、失败、排除和环境限制。
- UI 或行为变化需要的演示材料；无视觉变化时明确说明不适用。
- 最新提交后的人工或自动审查请求。

创建后重新读取公开 PR，确认 Base、Head、状态、Issue 关联和审查评论真实存在。外部 Bot 因额度、权限或仓库配置未运行时如实报告，不替它宣称通过。

## 8. 完成通知

只有用户要求通知，或通知属于明确验收条件时才发送。

- Bark URL、设备 Key 和其他通知凭据只从环境变量、系统安全存储或用户当次明确输入读取。
- 不把通知凭据写入仓库、日志、命令输出、任务元数据或长期记忆。
- 找不到配置时，不猜测端点，也不扫描 shell 历史；完成其他可达工作后再询问用户。
- 给用户三个清晰选择：提供安全配置、跳过通知、改用本机通知。
- 本机快捷指令不可用时，可以使用系统原生通知作为已授权回退。
- 回退通知必须按真实渠道报告；macOS 本机通知不能称为 Bark 已送达。

## 9. 完成检查表

- [ ] Issue 当前仍有效，公开重叠工作已经排除或说明。
- [ ] PR 范围最小；多 Issue 合并有不可分割的技术理由。
- [ ] 修复覆盖根因和边界，不靠隐藏症状。
- [ ] 必要的独立审查已经基于最终代码完成。
- [ ] 测试、构建和排除项按实际结果报告。
- [ ] PR 模板、Issue 关联和公开状态已经核验。
- [ ] 完成通知使用真实渠道，凭据没有泄露。

## 反模式

- 只看 Issue 标签，不搜索 PR 和当前主线。
- Issue 仍为 Open，就默认缺陷仍存在。
- 为了凑齐任务数量，重复修改已经正确的代码。
- 默认把多个无关 Issue 放入一个 PR。
- 用测试数量、Agent 数量或 Bot 评论数量代替行为证据。
- 遇到失败只换命令，不区分代码、工具链、环境和既有问题。
- 隐瞒排除项，或把部分门禁包装成全量通过。
- 创建 PR 后不核对公开状态和关联结果。
