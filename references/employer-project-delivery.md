# 雇主与商业项目交付

## 适用范围

任务来自雇主、客户、合作团队，服务于商业交付、试用期目标、绩效结果或线上业务时，使用本流程。重点不是展示工程量，而是尽快得到可验证结果，并让进度、风险和下一步能被非技术决策者直接理解。

## 1. 先确定结果

开始前从任务、仓库、文档和现有系统中确认四件事：

- **目标**：这次工作要改变什么业务或用户结果。
- **验收证据**：什么可观察结果能证明目标成立。
- **主路径**：从真实入口到最终结果必须经过哪些最少环节。
- **边界**：明确期限、环境、权限和不能触碰的数据或合规红线；已有资料足够时直接推进，不重复询问。

技术方案、文件数量、测试数量和提交数量都不是目标。无法映射到验收证据的工作默认后置或删除。

## 2. 前期先跑通真实主流程

初始阶段默认完成最小垂直闭环，而不是先铺完整架构、覆盖全部边界或做大规模重构：

1. 排除阻止启动和联调的环境、权限、依赖问题。
2. 使用目标环境或最接近目标环境的配置、代表性账号和数据，跑通“真实入口 → 核心处理 → 真实依赖或持久化 → 用户可见结果”。
3. 保存足以复核的结果证据，明确哪些环节真实、哪些环节因外部条件尚未验证。
4. 主流程首次跑通后，再按风险补异常路径、兼容性、性能、可观测性、重构、文档和扩大验证范围。

“跑通”不等于“完成”。Mock、静态页面、只编译成功或只调用单个接口，不能冒充端到端闭环；实验可以使用替身，但必须显式说明证据边界。

以下门禁不能为了赶主流程而后置：数据丢失、越权或密钥泄露风险；法律、合同和公司合规要求；不可逆数据库变更；无法可靠回滚的生产切流。它们存在时先做最小阻断处理，再继续主线。

## 3. 风险转成待办，不让旁路拖散主线

执行中发现的风险、未知项、旁路缺陷和后续优化，不反复写成长篇提醒；每一项转成一个可执行待办：

- 待办以动作开头，只描述一个可验证结果，例如“核对 Production 迁移回滚路径”，不要写“注意数据库风险”。
- 能记录元数据时补充证据或触发条件、影响、下一动作和状态；不能记录时至少保证任务名能说明要消除什么风险。
- 阻塞当前验收、需要用户或雇主决定、可能造成安全/合规/数据损失/生产事故或影响明确期限的风险，立即升级并标记为阻塞。
- 不影响当前主路径的风险进入待办队列，继续主线；到相关决策点、发布前或阶段收尾时再提醒。
- 无关既有问题单独记录，不借风险名义扩大本次范围。
- 只有得到对应证据后才能完成待办；“已知晓”“以后处理”不算完成。

提醒只报告新增、状态变化或即将触发的风险。相同风险没有变化时不在每轮回复里重复。

## 4. 适时生成可直接向上汇报的话术

在以下节点，若任务与雇主或客户交付有关，附一段“可直接向上汇报”；普通工具调用、无结果的中间步骤和重复状态不生成：

- 真实主流程首次跑通。
- 一个关键里程碑完成，或范围、优先级发生变化。
- 阻塞需要上级决定、资源或跨团队支持。
- 阶段交付完成，结论已由证据支持。

话术控制在二到四句，默认包含目标、已验证结果、业务价值、剩余风险和下一步或所需支持。使用可直接转发的职业表达，不写命令、文件路径、内部排查流水账，不用测试数量和工作时长证明价值，不虚构进度、期限或确定性。

### 正常进展

> 本阶段目标是【目标】。目前已跑通【关键流程】，并通过【验收证据】确认【结果】；现阶段已具备【业务价值】。剩余【风险】已进入待办，【是否影响当前目标】；下一步推进【下一里程碑】。

### 需要支持

> 主流程已推进到【当前节点】，当前受【阻塞】影响【范围或期限】。已完成【已验证工作】并排除【关键非原因】；现需要【决策人或团队】确认/提供【具体事项】，之后即可继续【下一步】。

### 阶段完成

> 已完成【交付结果】，关键流程已通过【真实场景或证据】验证，现可支持【业务结果】。尚余【非阻塞事项】已列入待办，不影响【当前可用范围】；下一阶段聚焦【下一目标】。

模板只提供结构，输出时应改成自然短句；没有剩余风险或不需要支持时直接删除对应句子，不能为了填模板制造内容。

## 5. 阶段检查

每个里程碑只检查与目标有关的状态：

- 主流程是否真实跑通，还是只有局部组件绿色。
- 当前证据是否足以支持对外结论。
- 阻塞风险是否已经升级，非阻塞风险是否都有待办。
- 下一动作是否直接缩短到验收结果的距离。
- 向上汇报是否讲结果和影响，而不是讲忙碌程度。

## 6. 长任务保留可回滚成果

雇主项目周期较长、包含两个以上可独立验证的结果时，在获得 Commit 授权后主动按里程碑提交：

- 在任务计划中标出自然提交边界，例如“真实接口闭环”“消费者可见结果”“发布与线上验收”；跨层契约不可独立工作时保持在同一提交。
- 每完成一个边界并取得对应证据就提交，不等全部优化和旁路待办清零。
- 提交前只暂存本阶段文件，确认没有混入他人改动、凭据、临时产物或已知失败。
- 阶段提交必须保持可理解、可验证和可回滚；不用 `WIP`、空壳或只为保存进度的坏提交凑数量。
- 尚未处理但不影响当前正确性的风险留在待办；影响当前提交成立的风险先解决，不能用待办掩盖坏快照。

分批提交的目标是缩短回滚和审查半径、保住已经验证的成果，不是用 Commit 数量包装产出。最终 Push、PR 或 Release 前仍需验证组合后的最终状态。

## 反模式

- 前期先搭通用平台、完整抽象或全量测试，主流程长期不可用。
- 用 Mock、截图、编译通过或单接口成功宣称系统已经跑通。
- 风险只写在聊天和日志里，没有对应待办、负责人或下一动作。
- 每轮重复同一风险，制造焦虑但不推动决策。
- 向上汇报只罗列改了多少文件、跑了多少测试、投入多少时间。
- 把非阻塞待办包装成已完成，或为了显得顺利隐瞒真实阻塞。
